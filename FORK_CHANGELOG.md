**Known gaps with the conventions** (to fix in a dedicated pull request)

- Upstream permission logic is replaced, not kept: `allowPermissions([ADMIN, MEMBER], PROJECT)` becomes `canEditProjectWorkItems` in 28 core files. A single seam (the fork permission store treating a collaborating guest as a member for project-level checks) would bring them back to upstream.
- Fork logic is added to upstream backend code instead of `plane.extended`: the `allow_permission` decorator, six views and the project serializers (the same method copied twice). Handling the flag once in the decorator would remove the view changes.
- Lint and unrelated changes in upstream files: file-level `// oxlint-disable` comments, and `.sort` replaced by `.toSorted` in `project-navigation.tsx` (fixed on `chore/clean-fork-upstream-sync`).
- Plane offers no such feature as such (closest: guest custom roles on Enterprise). It needs either an entry in "Features not in Plane" or a decision that the Enterprise equivalent covers it.

## Features not in Plane

### Guest collaboration

- **Not in Plane**: Plane's project Guest cannot see or create work items; its Commenter role (Pro and above) can view and comment but not edit. No plan lets a guest create work items and use cycles and modules on a project. Closest: custom roles (Enterprise, "Custom roles via RBAC + GAC").
- **Why built anyway**: clients and external contributors work in the projects of a shared workspace and must not see the other clients' projects, which the Member role would open to them.
- **Decided by**: built before the feature check existed (#3, #4); recorded on 2026-11-10 when LONESTONEP-4 extended it.
- **Upstream files**: see "Guest collaboration" under "Upstream files touched".

### Assign work items to guests (LONESTONEP-4)

- **Not in Plane**: no plan documents assigning a work item to a guest. Community Edition only has `guest_view_all_features`, which lets guests see every work item of a project.
- **Why built anyway**: hand a work item to a client or an external contributor, who finds it in their own space, without giving them the Member role.
- **Decided by**: Loïc Vanderschooten, on 2026-11-10.
- **Upstream files**: `apps/api/plane/app/serializers/issue.py`, `apps/api/plane/app/serializers/draft.py`, `apps/web/core/components/dropdowns/member/dropdown.tsx`, `apps/web/core/components/issues/issue-layouts/utils.tsx`, `apps/web/core/components/power-k/ui/pages/context-based/work-item/root.tsx`, and keys appended to `packages/i18n/src/locales/{en,fr}/work-item.json` (details under "Upstream files touched").
- **Gap with the ticket**: Plane keeps "Your work" to workspace admins and members, so an assigned guest finds the work item in the project's views, not in "Your work".

### Installable PWA (LONESTONEP-3)

- **Not in Plane**: no plan offers a PWA (plane.so/pricing lists neither PWA, mobile nor offline). Plane serves phones with native iOS and Android apps, which only work with Plane Cloud and the commercial self-hosted edition (docs.plane.so/devices/mobile). Upstream still ships PWA leftovers: two web manifests and PWA meta tags in `apps/web/app/root.tsx`, and an old next-pwa `sw.js` that nothing registers.
- **Why built anyway**: the native apps do not work with our Community Edition, so the browser is the only way to use Plane on a phone. Installing it from the browser, full screen, mostly reuses what upstream already ships. Offline use is out of scope (LONESTONEP-13).
- **Decided by**: Tatiana Grange, on 2026-11-17.
- **Risk on upstream merges**: if Plane ships its own PWA again, it would clash on `site.webmanifest.json`, `metadata.ts` (`SITE_NAME`) and `entry.client.tsx`, and two service workers would compete for the scope `/`: keep only one. Upstream already changed the icons of `site.webmanifest.json` (to `icons/icon-192x192.png` and `icon-512x512.png`, as here): expect a small conflict there. If upstream reorders or drops the manifest links in `root.tsx`, re-check which manifest browsers use.
- **Upstream files**: `apps/web/app/entry.client.tsx` (two lines), `packages/constants/src/metadata.ts` (one line), `apps/web/public/site.webmanifest.json` (icons), and three added files in `apps/web/public/` (details under "Upstream files touched"). `root.tsx`, `manifest.json`, the old next-pwa `sw.js` and `workbox-*.js` stay as they are.

### Attachments from the work item modal (LONESTONEP-16)

- **Not in Plane**: no plan lets the work item modal add attachments; the request (makeplane/plane#4088) was answered with the `/attachment` editor block (Pro and above), which puts the file in the description.
- **Why built anyway**: the ticket asks for attachments when creating a work item, and a file belongs in the work item's attachments, with those added later with "Attach", not at a place in the text. Images still go in the text with a paste or `/image`.
- **Decided by**: Tatiana Grange, on 2026-11-24. A first version built Plane Pro's `/attachment` block (local branch `wip/lonestonep-16-editor-block`); dropped for this one.
- **Gaps**: hidden for drafts (Plane converts a draft's files to description assets); a file whose upload fails after the work item is created is named in a message, to add again with "Attach".
- **Risk on upstream merges**: if Plane fills `handlePropertyValuesValidation` or `handleCreateUpdatePropertyValues` in CE (its custom properties), the provider must call both its code and the fork's. If the description field leaves `.editor-container`, or the modal stops being a `role="dialog"`, the list and the drop overlay no longer show: covered by `apps/web-e2e/tests/modal-attachments.spec.ts`.
- **Upstream files**: `apps/web/core/components/issues/issue-modal/provider.tsx` (two swapped placeholders: the modal context's validation and create/update callbacks), `modal.tsx` (one line) and keys appended to `packages/i18n/src/locales/{en,fr}/work-item.json` (details under "Upstream files touched").

### Inbox archive all (LONESTONEP-14)

- **Not in Plane**: no plan archives every notification of the inbox at once, nor offers a multi-select on notifications (docs.plane.so/core-concepts/inbox; plane.so/pricing has no inbox row, its "Bulk Ops" are for work items). Community Edition archives one notification at a time and has "Mark all as read" in the inbox header. Closest: stacked notifications (Pro), where archiving a stack archives every notification of one work item.
- **Why built anyway**: the inbox fills up faster than it can be archived one card at a time, and "Mark all as read" does not empty it.
- **Decided by**: Tatiana Grange, on 2026-11-25.
- **Risk on upstream merges**: if Plane ships its own "Archive all", it will clash in the inbox header (`sidebar/header/options/root.tsx`): keep only one button.
- **Upstream files**: `apps/web/core/components/workspace-notifications/sidebar/header/options/root.tsx` (one import, one line), and keys appended to `packages/i18n/src/locales/{en,fr}/notification.json` (details under "Upstream files touched").
- **Behaviour**: the button archives what the inbox view shows (tab, type and unread filters), loaded pages or not, after a confirmation. Snoozed notifications stay; the button is hidden in the archived and snoozed views.
